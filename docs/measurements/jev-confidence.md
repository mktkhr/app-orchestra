# Jev の確信度は正解率を表しているか（机上の仕分け直し）

- 日付: 2026-09-18
- 模型呼び出し: なし（保存済みの記録のみを使用）
- 行データ: `raw/jev-confidence-rows.jsonl`（二回分 × 百問 = 二百行。`run`, `id`,
  `question`, `answers`, `jevChoice`, `jevConfidence`, `jevCorrect`, `localChoice`,
  `localCorrect`）

## 問い

判断模型（Jev）は選択と一緒に確信度（〇〜一）を返す。これまでの試験では閾値を
〇・五と〇・七に根拠なく置いた。実運用事例（`jev-field-report.md`）では〇・九が
使われていたが、これも根拠の記載がない。確信度が高い時、実際に正解率は高いか。
高いなら、どの閾値で判断模型に任せ、残りを自前に回すのがよいか。

## 使った記録

- `jev-picker-v1-corpus-picks.jsonl`（初回の書き方、百問）
- `jev-picker-v2-corpus-picks.jsonl`（説明を厚くした書き方、百問）
- 正解の鍵と自前側の答え: `jev-chip-order-rows.jsonl`（`answers`, `localChoice`,
  `correctAt1`）

正解の判定は「判断模型の選択そのもの」が正解の鍵に含まれるか。製品としての最終
回答（組み込みの選択肢に対する自前側の後処理を含む）ではない。このため初回の
正解数は 59 で、以前の記録の 69（後処理込み）とは異なる
（`jev-language-v4.md` の注記参照）。

未満の行は自前の答えで数えた。判断模型側は「選択そのもの」、自前側は「最終回答」で

## 読み取れること

1. 確信度は正解率と同じ向きに動いている。閾値を上げるほど、閾値以上の正解率は
   上がる（初回 67% → 95%、厚く 74% → 90%）。ただし帯ごとに見ると単調ではない
   （初回の 0.4–0.5 帯が 18%、厚くした回の 0.8–0.9 帯が 77%）。百問では帯あたり
   の件数が少なく、細かい較正の議論はできない。
2. 説明を厚くした回は、確信度 0.9 以上の件数が 11 から 26 に増えたが、その帯の
   正解率は 90% から 84% に下がった。`jev-picker-v2.md` の「確信度は上がったが正解
   率は付いてこなかった」を、閾値の側から見た同じ現象である。
3. 組み合わせの試算は、どの閾値でも自前のみの 78 を超えなかった。初回で 0.8 以上、
   厚くした回で 0.7 以上を任せると 78 と同点。判断模型に任せた行で自前も正解して
   いることが多く、任せても増えない。
4. 同点で任せる件数が最大になるのは、厚くした回の閾値 0.7（49 件、約半数）。正解
   数を落とさずに、約半数の質問を自前の演算装置から外せる、という読み方はできる。
   これが速さや同時利用の面で意味を持つかは `latency-bench.md` の結果次第。
5. 実運用事例で使われていた 0.9 は、この記録では「任せる件数が少なく（11 または 26
   件）、同点か一問負け」に当たる。

## この記録で分からないこと

- 閾値未満の行を自前に回した時、自前が実際に何を答えるか（試算は、同じ質問に
  自前が単独で答えた記録を流用している）。
- 質問が百問に限られるため、帯ごとの正解率の揺れは偶然の範囲を出ない可能性が高い。
- 判断模型の同じ条件での再実行による確信度の揺れ（`jev-picker-v1.md` で同条件の
  別実行が 2/10 と 6/10 に分かれた行がある）。
