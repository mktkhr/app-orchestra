# Four Claude models through the product's own planner - a single-shot check

Measured 2026-09-18 at `adbdf6b`. Not a comparison run: six questions per
model, enough to prove the path works, to see where each model differs from
the local default, and to price a full run from real token counts rather
than an estimate.

## Why this exists

The last frontier measurement (`DECISIONS.md`, 2026-09-15) sent one
`POST /v1/messages` per question against a 50-candidate shortlist with a
stand-in script - it measured the pick alone, on a tree that no longer
exists (single-stage planning, no `v6-unmatched-filter`, an 18-case eval).
This round instead points **the product's own planner** at the Anthropic
Messages API: both stages - the pick and the fill, tools and all - with
local narrowing (`e5-large-q8` + `bge-reranker-v2-m3-q8`, K=20) unchanged
in front of them.

`adbdf6b` adds that backend: `ORCHESTRA_LLM_PROVIDER=anthropic` with
`ORCHESTRA_LLM_MODEL=<claude id>` and `ANTHROPIC_API_KEY` from the
process environment. Unset, the tree is byte-identical to before.

## The API rules this round had to respect

All four came out of the official documentation before any paid call, and
each one has a cost attached to getting it wrong:

- **`temperature` is rejected (400) on `claude-sonnet-5`, `claude-opus-5`
  and `claude-fable-5-1`.** The planner sends temperature 0 on every call,
  so the backend has a per-model table that omits it for those three and
  keeps it for `claude-haiku-4-5`.
- **Sonnet 5 and Opus 5 think by default**; the backend sends
  `thinking: {"type": "disabled"}` for them. Haiku 4.5 does not think
  unless asked. **Fable 5.1 cannot be told not to think** - any explicit
  `thinking` configuration is a 400 - so nothing is sent.
- **Thinking tokens count against `max_tokens`.** The 2026-09-15 round
  wasted $1.37 by setting `max_tokens: 64`: 65 of Opus's 100 answers came
  back empty. This round kept the planner's own budgets (1024 fill / 200
  pick) and asserted `stop_reason` and `usage` on every call.
- **Model ids carry no date suffix** (`claude-haiku-4-5`, not
  `claude-haiku-4-5-20251001`).

No 400, no empty answer, no truncation and no refusal occurred in any of
the 40 calls below.

## The six questions

Chosen to cover one behaviour each: an enum filter, no filter, a
restricting word the enum does not have, an out-of-domain question, a
capability question, and a cross-service id.

| question               | local `qwen3.5-9b-q8`                      | Haiku 4.5                   | Sonnet 5 | Opus 5 | Fable 5.1 |
| ---------------------- | ------------------------------------------ | --------------------------- | -------- | ------ | --------- |
| 検品保留の在庫を見せて | `ListInventoryItems {status: quarantined}` | same                        | same     | same   | same      |
| 在庫を全部見せて       | `ListInventoryItems {}`                    | same                        | same     | same   | same      |
| 破損した在庫はある？   | **ask on `status`**                        | **`ListInventoryItems {}`** | ask      | ask    | ask       |
| 今日の天気は？         | `none`                                     | same                        | same     | same   | same      |
| 在庫で何ができる？     | `list_capabilities`                        | same                        | same     | same   | same      |
| att-002の内容          | `GetAttendanceRecord {id: att-002}`        | same                        | same     | same   | same      |

**One divergence, and it is the interesting one.** 破損 is not an
`ItemStatus` value; the product's contract (`PRODUCT.md` AC-B-105, and the
`v6-unmatched-filter` wording adopted 2026-09-16) says an unmatched
restricting word must become a question, never a silently dropped filter.
The local 9B, Sonnet 5, Opus 5 and Fable 5.1 all ask. Haiku 4.5 returns
every row instead - the exact failure the wording change was written to
close, reappearing on a different model with the same prompt. A prompt
fix is not model-independent.

## Cost and latency, measured

Ten calls per model (six questions; four of them take a pick and a fill,
two resolve at the pick).

| model                 | input tok | output tok |    cost | per-question latency |
| --------------------- | --------: | ---------: | ------: | -------------------- |
| local `qwen3.5-9b-q8` |         - |          - |      $0 | 0.3-1.2 s            |
| `claude-haiku-4-5`    |     9,853 |        304 | $0.0114 | 1.7-5.6 s            |
| `claude-sonnet-5`     |    10,314 |        571 | $0.0263 | 1.8-6.3 s            |
| `claude-opus-5`       |    10,042 |        516 | $0.0631 | 1.9-7.2 s            |
| `claude-fable-5-1`    |    10,062 |        529 | $0.1271 | 4.8-11.1 s           |

Round total **$0.2279**; cumulative Anthropic spend **$4.03** of the $20
budget.

Every Claude model is slower than the local 9B on this task - network plus
a larger model - and Fable 5.1, which always thinks, is four to ten times
the local model's latency.

## What a full four-instrument run would cost

From the measured rate (~1,670 input and ~50 output tokens per question,
two calls each), the four instruments are 527 questions:

| model              | eval + corpus + mid + dialogues |
| ------------------ | ------------------------------: |
| `claude-haiku-4-5` |                           ~$1.0 |
| `claude-sonnet-5`  |                           ~$2.0 |
| `claude-opus-5`    |                           ~$5.1 |
| `claude-fable-5-1` |                          ~$10.2 |

All four would be ~$18.3 against $16 of remaining budget; Haiku + Sonnet +
Opus is ~$8.1 and fits. Not run - this round is the single-shot check only.

## What this does and does not say

- The backend works end to end for all four models, both planner stages,
  with tools - that is the thing this round set out to prove.
- Six questions do not rank models. Sonnet 5, Opus 5 and Fable 5.1 are
  indistinguishable here; the only visible difference in the whole round is
  Haiku's dropped filter.
- The 2026-09-15 numbers (Haiku 67, Sonnet 73, Opus 73 against the local
  69, pick-only, 50 candidates) are not comparable to today's tree and are
  not restated here.
